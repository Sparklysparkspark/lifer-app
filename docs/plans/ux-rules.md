# Lifer UX rules

These rules come from every UI and UX correction the maintainer has made so far: about 1,060 comments in past Claude sessions (2026-08-19 to 2026-10-22), plus the git history, the UX plans (`world-class-ux.md`, `ux-backlog-2026-10-21.md`, `ux-workflow-teardown.md`) and the saved feedback notes. Each rule is a pattern he has had to point out more than once, or once with a clear general principle behind it.

**How to use it**

- Every worker reads this page before starting UI work, and names in their brief the rules the change touches.
- Before reporting UI work done, take screenshots (light and dark, smallest window, a large window, and seeded extreme data) and check them against the rules. Report which rules were checked.
- Reviewers check the screenshots against the rules, not only the code.
- Rules marked LINT or E2E should become automated checks (see [Proposed checks to build](#proposed-checks-to-build)). Rules marked VISUAL need a reviewer with screenshots. HUMAN rules are taste calls only the maintainer makes; ask rather than guess.

Frequencies are approximate counts of separate comments about the same pattern. "Existing check" names what already catches it today.

## Notes

- **Counts are approximate.** Nitpicks were pulled from long, messy transcripts by reading the maintainer's own words only (pasted logs and pasted ChatGPT text were skipped, and a few very long messages were cut off in the extracts). Many comments repeat the same pattern across days; each repeat was counted once per session day.
- **Reversed decisions.** Some preferences changed: sidebar icons were removed and later restored (2026-10-19); the header went from a colour experiment back to white (2026-08-23); the accent went to white and back to yellow (2026-10-13 and 10-14); the info panel in the viewer was added then removed. When a rule touches these, follow the latest decision and ask if unsure.
- **Hover style.** He prefers a subtle fill change over a drop shadow for hover (2026-08-21), and underline for clickable headings (2026-10-22). The E2E hover check only proves something changes; whether it is the right change stays VISUAL.
- **Collapsible sections** went both ways on the species page (2026-10-13 asked for collapsible facts, 10-14 asked to remove one collapse but make the whole About section collapsible). Treat as HUMAN.
- **Translucent headers.** He liked the slightly transparent sticky header (2026-10-19) but disliked content ghosting through the title bar gradient (2026-09-08). The line is: translucent is fine, readable content showing through the window controls area is not.
- **Search quality** is partly a data and model question rather than UI; the rules here cover only the behaviour people see. The golden-query E2E needs a fixed seed so results are deterministic.
- **Data correctness rules (U2, U3)** depend on the catalog pipeline; the UI side is to hide labels it can't trust and to fall back rather than show a wrong image.
- **Already covered well:** em dashes, literal strings (i18n lint), icon-button names, token contrast, species name display, card-name fitting at the smallest size, duplicate card photos and map framing. Don't rebuild these.
- **The maintainer's process asks** (2026-09-14 "Stop cutting corners, look at the import page... and actually do what I've asked"; 2026-09-13 "Verify every requested change actually landed") aren't UI rules, but they are why the HIG screenshot review exists: open the referenced component, copy it exactly, and check the built app before reporting done.
